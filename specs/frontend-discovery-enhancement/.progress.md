## Learnings

- **Generic architecture is essential**: Core adapters must have zero HomeAssistant-specific code; HA-specific logic lives in extension plugins
- **ExtractorAdapter protocol is the pattern**: New TypeScriptAdapter should follow the existing `parse_file()` / `extract_dependencies()` interface
- **Plugin architecture for extractors**: LitComponentExtractor, I18nKeyExtractor, ServiceCallExtractor as pluggable plugins on TypeScriptAdapter (not separate adapters)
- **Output schema contract**: All extractors must declare output schema; this is critical for ChatML JSONL generation downstream
- **file_globs vs profile_extensions**: Only profile_extensions (suffix matching) is implemented; file_globs pattern support is NOT implemented
- **Regex fallback is explicit acceptance**: Research shows 85% coverage acceptable for v1, with AST as upgrade path
- **TranslationJsonParser is standalone**: Not part of TypeScriptAdapter; separate parser for JSON files that feeds i18n key-value pairs
- **ChatML JSONL requires schema validation**: Each message role (system/user/assistant) has distinct content structure; must validate before export

- **Service call pattern**: `hass.callService(domain, service, serviceData)` - always string literals for domain/service
- **Variable prefixes**: `this.hass` (TypeScript), `context._hass` (Bubble-Card JS), `hass` (function param)
- **Domains found**: cover, light, climate, media_player, fan, lock, vacuum, humidifier, update, input_number, input_select, select, number, alarm_control_panel
- **ServiceData always includes `entity_id`** when targeting specific entity
- **No Python AST for TS/JS**: Must use regex fallback or Node.js esprima/tree-sitter
- **Regex coverage**: ~85% for literal string patterns; misses variable interpolation
- **TypeScript interface confirmed** at `custom-cards/button-card/src/types/homeassistant.ts:159`

## i18n Research Learnings (from .research-i18n-patterns.md)

- **Key patterns found**: `localize('ui.xxx')`, `hass.localize("ui.xxx")`, `localize('state.xxx')`, `localize('component.xxx')`
- **Dynamic keys**: ~20% use template literals - only prefix extractable (e.g., `localize(\`ui.card.${action}\`)`)
- **HomeAssistant i18n structure**: Nested JSON with dot-path keys (e.g., `mfa_setup.totp.step.init.title`)
- **ICU message format**: Supported via `IntlMessageFormat` - syntax: `{name}`, `{count, plural, =0 {Zero} other {#}}`
- **Translation file locations**: Backend `strings.json` at `core/homeassistant/components/{domain}/strings.json`; frontend localize wrappers in custom-cards
- **Leaf detection**: Objects with only string values are leaves; nested dicts are intermediate categories requiring recursion
- **Key-text mapping**: Flatten nested JSON first, then build reverse lookup (same text can appear under multiple keys - needs context)
- **Recommended extraction**: Static keys via AST/regex; dynamic key prefixes via template literal analysis; translation JSON via recursive flattening

## Lit Parsing Research Learnings (from .research-lit-parsing.md)

- **@customElement decorator**: `CallExpression` with callee `Identifier` name='customElement', tag name in arguments[0] as `StringLiteral` or `Identifier` (constant ref)
- **@property decorator options**: `type`, `attribute` (custom attr name), `reflect` (to attribute), `state` (reactive vs non-reactive)
- **@state decorator**: Same as @property but implicitly `state: true`
- **AST libraries ranked**: tree-sitter (most robust) > typescript-estree > @babel/parser > regex fallback
- **Observed attributes**: Derived from @property defaults (lowercase name) or explicit `attribute: 'custom-name'` option
- **Class hierarchy**: Component extends `LitElement` - can detect via `superClass.name === 'LitElement'`
- **Service call AST structure**: `CallExpression` with `callee.type === 'MemberExpression'` where `callee.property.name === 'callService'`
- **callService arguments**: [0]=domain (string/Identifier), [1]=service (string/Identifier), [2]=serviceData (ObjectExpression), [3]=target (ObjectExpression)
- **Decorator detection challenges**: Namespace imports (`import { customElement }`), aliased imports (`import { customElement as ce }`), constant references for tag names
- **Generic parser architecture**: ExtractorAdapter protocol + pluggable LitExtension + HomeAssistantExtension (follows existing pattern)

## Learnings

### Requirement insight from analysis 1: Fragment Types Coverage
- **Type 1 (FUNCTIONAL_UNIT)**: WORKING - pairs logic + test, size gate bypassed when test exists, uses `[ARCH_HEADER]` for dependencies
- **Type 2 (FUNCTIONAL_UNIT_WITH_CONTEXT)**: INTENTIONALLY NOT IMPLEMENTED - removed during Phase 6, README content folded into MODULE_BLUEPRINT (TIPO 4)
- **Type 3 (LOGIC_ONLY)**: WORKING - size-gated standalone files (≥1000 chars), Python files additionally filtered by `GOLD_PATTERNS`
- **Type 4 (MODULE_BLUEPRINT)**: WORKING for ALL LANGUAGES - always emitted per module, includes `[MODULE_MAP]`, `[DEPENDENCIES]`, `[SCHEMA]`, `[VOCABULARY]`, `[README]`
- **Type 5 (GOVERNANCE_RULES)**: WORKING - extracted at repository root level before module processing, uses `[GOVERNANCE_HEADER]`

### Requirement insight from analysis 2: Adapter Selection Pattern
- **Per-file selection is implemented** (Phase 7 fix): `metadata_enricher.py:495-496` shows `adapter = get_adapter(mf.path.suffix)` followed by `adapter.parse_file(mf.path)`
- **Adapter routing by extension**:
  - `.py` → `PythonAstAdapter`
  - `.ts`, `.tsx` → `TypeScriptAdapter`
  - `.php` → `PhpLegacyAdapter`
  - `.yaml`, `.yml`, `.jinja` → `YamlAdapter`
- **Discovery strategy ≠ file filtering**: Discovery strategy (manifest, init, typescript, yaml, filesystem) determines which architecture blueprint to aggregate, but does NOT filter which files are processed
- **All files with adapters are processed**: If a repository has `.ts` files and `TypeScriptAdapter` is registered, those files are processed regardless of whether the repo profile is "python" or "yaml"

### Requirement insight from analysis 3: MODULE_BLUEPRINT Cross-Language
- **TYPE 4 works for all languages**: MODULE_BLUEPRINT aggregation works for Python (manifest.json/__init__.py), TypeScript (directory scan with anchor detection), YAML (yaml strategy with strings.json anchor), PHP (filesystem with anchor detection)
- **README inheritance pattern**: If a module lacks a README in its directory, the processor walks up the tree toward repository root and inherits the first README.md/README.rst/README.txt found
- **Anchor file special handling**: `const.py` → `[VOCABULARY]`, `services.yaml` → `[SCHEMA]`, `manifest.json` → `[DEPENDENCIES]`, `strings.json` → raw content

### Requirement insight from analysis 4: Size Gate Configuration
- **MIN_SIZE (200 chars)**: General minimum size for any logic file (bypassed if test exists)
- **LOGIC_ONLY_MIN_CHARS (1000 chars)**: Threshold for Type 3 standalone emission
- **MAX_SIZE_BACKEND / MAX_SIZE_FRONTEND**: Repository-type-specific caps to prevent oversized modules
- **GOLD_PATTERNS filter**: Only applies to Python files without tests (keeps legacy behavior)

### Requirement insight from analysis 5: Test Detection Logic
- **Mirror-based detection**: Test file is found by name mirror (`module.py` → `test_module.py`) OR in `tests/` directory (`tests/test_module.py`)
- **Size gate bypass for tested code**: Files under `MIN_SIZE` are still emitted as Type 1 if a test exists (teaching tests is valuable)
- **Test files are context only**: Test files are included in Type 1 bundles but are NOT emitted as standalone Type 3 fragments

### Requirement insight from analysis 6: Parse Error Handling
- **Configurable policies**: `on_parse_error` setting supports `abort`, `skip`, `mark_and_continue`, `fallback`
- **Metrics tracking**: Parse errors are tracked in `_stats["parse_errors"]` and reported via `_metrics.increment_parse_error()`
- **Mark and continue**: Files with parse errors can be marked for manual review but processing continues

### Requirement insight from analysis 7: Discovery Strategy Detection
- **manifest strategy**: Home Assistant integrations with `manifest.json` (Python-specific anchor pattern)
- **init strategy**: Python packages with `__init__.py` as anchor
- **typescript strategy**: Repositories with >50 `.ts`/`.tsx` files, uses directory scan (no anchors)
- **yaml strategy**: Repositories with >5 `.yaml`/`.yml`/`.jinja` files (Home Assistant frontend discovery)
- **filesystem strategy**: PHP repos or any with `composer.json`

### Requirement insight from analysis 8: Out-of-Scope Clarifications
- **Type 2 explicitly removed**: Not a bug, not an omission - intentionally removed to simplify architecture
- **No repository-level adapter selection**: Phase 7 fix ensures per-file selection, not per-repo
- **No file filtering by discovery strategy**: Discovery strategy only determines architecture context aggregation, not which files to process
- **No custom adapter implementation in scope**: Only registering existing adapters in factory.py
- **One adapter per file**: Each file uses exactly one adapter based on its extension

### Requirement insight from analysis 9: Success Criteria Mapping
- **Fragment type generation**: All 4 implemented types (1, 3, 4, 5) must generate correctly for Python, TypeScript, PHP, YAML
- **Per-file adapter selection**: All file types must route to correct adapter regardless of repo profile
- **MODULE_BLUEPRINT across strategies**: Blueprint generation must work for all 6 discovery strategies
- **Test pairing**: Logic files with tests must be paired for Type 1 emission
- **Error resilience**: Parse errors must not abort entire repository unless policy is `abort`
